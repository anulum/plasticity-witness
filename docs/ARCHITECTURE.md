# Repository architecture

## Current executable tooling

Metadata, source-provenance, workflow, dependency-alignment, documentation, inventory and preflight controls inspect their declared local scopes. Native-tool bootstrap checks the selected executable and licence files. Received metadata cannot choose policy or grant numerical acceptance. Foundation qualification is in progress.

## Intended learning-evidence boundaries

| Component | Responsibility | Required evidence |
| --- | --- | --- |
| Protocols | Ordered events and whole prior population | Pairing, rate, applicable triplet and reward schedules, conditions and reset |
| Oracle | Independent published-rule and numerical reference | Read reference, justified equations, exact realization and short traces |
| Capture | Consume actual software or qualified capture observations | Full initial, intermediate and final state, ordering, gaps and timebase |
| Compare | Every update or supported distribution | Exact operation schedule or genuinely applicable source, trial and error method |
| Conditions | Bind each executed population cell | Actual concurrent load and declared learning-domain conditions |
| Report | Assemble full native record through installed shared provider | Whole raw/reference closure, numerical context and truthful verdict |
| Consumers | Independently replay and render the existing result | Installed separate consumer and actual Studio journey |

The planned report has eighteen required members: schema_id, claims, source_ref, environment_ref, rule, oracle, oracle_reference_ref, protocols, lane, fixed_point, load_conditions, fault_conditions, capture_ref, statistics, results, sc_report_refs, source_certificate_refs and verdict. This is a planned declaration, not registered or qualified domain support.

The four prospective library and CLI operations are run, analyse, report and verify. They are not installed or advertised as available commands. A separate consumer integration checks the resulting report; it is not another public command.

Actual source methods include pair-based RTL, reward-modulated RTL, floating-point triplet, encoded stochastic reward and encoded stochastic window updates. Preserve their complete constructors, initial state, reset and event order. RTL reads old right-hand-side state and later nonblocking assignments take precedence. Reward can use the previous eligibility state. Python triplet decay and weight-update order differs; its native timestep and time constants are milliseconds. Canonical seconds require explicit conversion.

Encoded stochastic methods retain both the output RNG and weight encoder, complete arrays with dtype, shape and bytes, window history, eligibility and call order. A zero scalar weight change can still advance the encoder. Window updates can consume a further random draw and ignore the newly inserted event when testing prior history. Scalar weight equality does not establish full-state equality.

The intended closed report requires fixed-point geometry and admits STDP or R-STDP rule kinds. Floating triplet output cannot be relabelled as exact fixed-point data. Unsupported representation or method remains unqualified; do not invent a conversion or erase the source method.

Exact comparison quantises at every declared operation point and retains the first mismatch. Distributional comparison requires actual scoped arithmetic and source support, trial protocol and applicable stopping rule. Passing batteries, selected seeds or encoded density cannot establish independence or statistical confidence.

Every required protocol and condition is planned before observation. Missing state, eligibility, raw population or instrument support remains inconclusive. A successful subset cannot establish an overall match. Measured fabric, RTL and software remain distinct. A learning result under a declared condition does not estimate reliability rates.
